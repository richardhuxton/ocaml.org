<h2><a href="https://anil.recoil.org/news.xml#tessera-embeddings" class="anchor" aria-hidden="true"></a>Tessera embeddings</h2>
<p>I've spent the week on a series of syncs over to <a href="https://source.coop">source.coop</a> from our old AWS bucket, and also from the Cambridge cluster, in order to converge all our <a href="https://anil.recoil.org/projects/tessera">TESSERA</a> embeddings in one place. Because there was so much data involved, it turns out that doing a conversion of the npy format to the <a href="https://anil.recoil.org/notes/tessera-zarr-v3-layout">Zarr v3 layout</a> would have taken about 4 months (due to our network link) for all eight years of embeddings if we did it from Cambridge!</p>
<p>Therefore <a href="https://www.tunbury.org/">Mark Elvers</a> and I <a href="https://www.tunbury.org/2026/08/03/week-31-2025/">investigated</a> the cheapest way of running the computation required to run AWS VMs. A naive computation using off-the-shelf on-demand EC2 VMs revealed it would cost around $40000, which seems a little high for our university budgets! However, after chatting to my old friend and colleague Andrew Peace (who works in the AWS S3 team) over coffee, he mentioned that spot instances can be quite cheap. I found <a href="https://aws.amazon.com/blogs/aws/aws-fargate-spot-now-generally-available/">AWS Fargate Spot</a> which allows for serverless containers to run whenever there is spare capacity in that region.</p>
<p>This required bundling up the <a href="https://anil.recoil.org/news.xml">geotessera</a> Zarr PR using <code>uv</code> and a Dockerfile. S3 secrets weren't required as Fargate has builtin support to 'grant' the container magic access to S3 without requiring an environment secrets dance. Once done, the conversion (one container per UTM zone) ran in parallel with very little drama.</p>
<p><img src="https://anil.recoil.org/images/aws-fargate-spot-usage.webp" alt="%c" title="The usage graph of the Fargate spot over a few days, about $500 (credit: Mark Elvers)"></p>
<p>The total cost? Around $557 including tax according to Mark! He had to run one or two zones on a non-spot Fargate, but the cost overall was massively lower than managing VMs on-demand ourselves. So perhaps EC2 should be for 'off demand' computing now...</p>
<p>After the conversion to Zarr was done, I spot checked the tile coverage by comparing the 1.1 and 1.0 embeddings, and you can see the results of having an expanded landmask below.  We probably won't backfill these for 1.0, preferring instead to get global coverage for <a href="https://anil.recoil.org/notes/tessera-v11-out">v1.1</a> (which our collaborators at dClimate are working hard on thanks to another AWS Open Data grant they got a few months ago).
I still also need to work on the meta-Zarr-index on source.coop, since there's no established standard for that; STAC might work but this is more fine-grained than that. The per-store layout at least follows the <a href="https://anil.recoil.org/notes/tessera-embeddings-convention">shared geo-embeddings convention</a> we moved to earlier in the year, so it's just the index across stores that's missing. It's on my list for next week to figure this out.</p>
<p><img src="https://anil.recoil.org/images/aws-fargate-spot-missing.webp" alt="%c" title="Checking for missing tiles in the manifests"></p>
<p>A nice overview of earth embeddings from <a href="https://konstantinklemmer.github.io/">Konstantin Klemmer</a> was published this week, titled simply "<a href="https://doi.org/10.1109/MGRS.2026.3710416">Earth Embeddings</a>". This is a great overview of geospatial earth embeddings from a broader perspective, including relating them to developments in LLMs. Konstantin gave an EEG seminar on <a href="https://www.cst.cam.ac.uk/seminars/list/211927">global geographical location encoders</a> back in 2024 and is moving to UCL in London, so I hope to hear more on this work as he settles in!</p>
<p>I also spent some pleasant time discussing <a href="https://anil.recoil.org/projects/life">habitat mapping</a> with both <a href="https://mynameismwd.org">Michael Dales</a> and <a href="https://aneeshnaik.github.io/">Aneesh Naik</a> who are <a href="https://digitalflapjack.com/weeknotes/2026-08-10/">making steady progress</a> on working through various strategies into a more unified map. <h3><a href="https://anil.recoil.org/news.xml#switching-to-django-and-capnp" class="anchor" aria-hidden="true"></a>Switching to Django and Capnp</h3>
<p>The index website I <a href="https://anil.recoil.org/notes/2026w31">built last week</a> is working well, but I needed something more sophisticated for managing the ingestion pipeline. The low-level logic for downloading each paper is <a href="https://tangled.org/anil.recoil.org/taposaur/tree/main/taposaur">working well</a> using my OCaml HTTP client (which offers useful low level control over how to <a href="https://tangled.org/anil.recoil.org/taposaur/tree/main/lib/services">handle each service</a> based on the good work <a href="https://www.lambdacambridge.com/robin-message">Robin Message</a> did earlier in the year).</p>
<p>But coordinating all this is quite difficult, since the filesystem layout contains roughly ~25 million files (and rapidly growing) and Ceph is too slow to spider incrementally with that many files. Therefore I've prototyped a Django and Celery based task queue, and exposed the paper downloader as a <a href="https://capnproto.org/">Capnp OCaml service</a> which the website can issue requests to.</p>
<p>This fits into the broader strategy in ETAP for building 'living evidence databases'. The idea here is that (for example) <a href="https://profiles.imperial.ac.uk/a.christie">Alec Christie</a> can also run a downloader node at Imperial for <em>their</em> living evidence database, using their own library credentials. However, multiple LEDs can share indices about what they have, including paper metadata and checksums, even though the fulltexts are closed. This will help build a network of users (initially just two, but we hope it'll grow) of libraries that are curating their own papers and allowing individual evidence synthesis groups to manage large groups of DOIs and filter them for quality control and AI slop.</p>
<p>I'll share more on this next week as my OCaml spider is churning away migrating to the new layout, which will take a few days of reindexing across all the papers!</p>

<h3><a href="https://anil.recoil.org/news.xml#ocaml-prometheus-refresh" class="anchor" aria-hidden="true"></a>OCaml Prometheus refresh</h3>
<p><a href="https://www.tunbury.org/">Mark Elvers</a> needs a Prometheus that works with eio, and so <a href="https://roscidus.com">Thomas Leonard</a> and I (with helpful review input from <a href="https://github.com/dinosaure">Romain Calascibetta</a>) spent some time on building a transition library. Since the core of the library has to stay independent of any concurrency library (and indeed, of Unix, so that it can run as a <a href="https://anil.recoil.org/projects/unikernels">unikernel</a>), we're working on two releases.</p>
<p>The first release is a minor <a href="https://github.com/mirage/prometheus/releases/tag/v1.4">1.4</a> that provides a simple compatibility upgrade path for existing users:</p>
<blockquote>
<p>This release is not a breaking change, but instead prepares for deprecation of Lwt in the core package so a future release can remove Lwt from the prometheus core. Users of the core's Lwt-typed functions should migrate to Prometheus_lwt now. Code using the new interface will keep working unchanged in future releases.</p>
<p>Add synchronous variants of the timing helpers to the core. Metric recording is synchronous and these will become the only core timing helpers once the Lwt-typed ones move to prometheus-lwt.</p>
</blockquote>
<p>The idea here is simply to add the future interface as an alias of the existing one, so that users who <code>opam upgrade</code> and get the new release will see deprecation warnings with instructions on what to do.</p>
<p>Once that's finished, I'm going to finish up the forthcoming prometheus 2.0 which <a href="https://github.com/mirage/prometheus/pull/65">moves Lwt out of the core</a> (into the module signatures created in <code>prometheus.lwt</code> in the 1.4 release) and subsequently integrate Mark's <a href="https://github.com/mirage/prometheus/pull/60">PR that adds Eio</a> as an independent package. It's quite a lot of work doing all this refactoring, but worthwhile I think! The core <code>prometheus</code> library remains entirely OS independent, using the <a href="https://github.com/mirage/mirage-mtime">mirage-mtime</a> library to obtain a portable clocksource for example.</p>
