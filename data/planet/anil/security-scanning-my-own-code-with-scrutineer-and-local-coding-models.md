<p>After the recent surge of <a href="https://anil.recoil.org/notes/rumour-is-the-exploit">security reports</a> in my projects, I wanted to help us open source maintainers use scanning tools to find bugs before the bad guys do. Luckily, <a href="https://nesbitt.io">Andrew Nesbitt</a> leapt in <a href="https://amok.recoil.org/@andrewnez@mastodon.social/117150259002007792">enthusiastically</a> with <a href="https://github.com/alpha-omega-security/scrutineer">Scrutineer</a>, a new project he's working on to help maintainers proactively manage the flood.</p>
<p>I decided to give it a quick spin. By default, Scrutineer supports a number of different coding models, but I remain blocked on access to <a href="https://www.anthropic.com/glasswing">frontier models</a> without security guardrails for our own code. Therefore, I decided to get a local coding model powered by <a href="https://huggingface.co/zai-org/GLM-5.3-Flash">GLM 5.3</a> running on my own Mac Studio. Read on if you want to set up your own instance; Scrutineer is worryingly good at finding lots of bugs!</p>
<h2><a href="https://anil.recoil.org/news.xml#what-scrutineer-does" class="anchor" aria-hidden="true"></a>What Scrutineer does</h2>
<p><a href="https://github.com/alpha-omega-security/scrutineer">Scrutineer</a> is a scanner built under the <a href="https://alpha-omega.dev">Alpha-Omega</a> project. It lets me add a Git repository or a whole org of them, and then schedules a big pipeline of agent scans via a swarm of ephemeral Docker containers. These scans include a first triage pass, then metadata analysis, dependency and SBOM extraction, static analysis with tools like <a href="https://semgrep.dev/">semgrep</a> and <a href="https://docs.zizmor.sh/">zizmor</a>, defining a threat model, and then a security deep-dive that does hours of analysis.</p>
<p>A web UI organises the (often raw) results for human triage, with a workflow designed to avoid <a href="https://alpha-omega.dev/blog/scrutineer-scanning-open-source-without-flooding-maintainers/">flooding maintainers with low-quality reports</a>. The agent CLI of choice is quite pluggable with Claude Code by default, with Codex, OpenCode and Copilot as alternatives (only one backend can be active at a time). Andrew kindly added an <a href="https://github.com/alpha-omega-security/scrutineer/pull/901">OCaml runner profile</a> days after my <a href="https://anil.recoil.org/notes/2026w34">earlier post</a>, so OCaml repositories now also have a specialised scanning container with our toolchains like opam installed.</p>
<p><img src="https://anil.recoil.org/images/scrutineer-ss-3.webp" alt="%c" title="The skill pipeline fanning out across parallel scans after the initial triage of cohttp."></p>
<p>I deployed it on an <a href="https://exe.dev">exe.dev</a> VM, a service I'm fast becoming a <a href="https://anil.recoil.org/notes/2026w30">fan of</a> due to its nice CLI and convenient HTTPS proxies. Scrutineer runs as a dedicated host process there, as every scan it does spawns a fresh Docker container so there's no point running the service itself in a container. The UI doesn't have any auth of its own, so for now it's using exe's <a href="https://exe.dev/docs/proxy">authenticated HTTPS tunnel</a>. I'm not sure how to set up a 'production' multiuser version of this yet, but it's early days and I return to this <a href="https://anil.recoil.org/news.xml#figuring-out-usable-workflows-here">below</a>.</p>
<p>Deploying it was extremely simple by following the docs, despite it being under rapid development. I submitted a minor fix to the Dockerfile (<a href="https://github.com/alpha-omega-security/scrutineer/pull/949">#949</a>) and upgraded <a href="https://github.com/git-pkgs/git-pkgs"><code>git-pkgs</code></a> to the latest one with opam support (<a href="https://github.com/alpha-omega-security/scrutineer/pull/950">#950</a>). The latter meant that Scrutineer could break down the individual opam dependencies that a repo depends on. For example, <a href="https://github.com/mirage/ocaml-cohttp">cohttp</a> went from 13 dependencies to 207, of which 194 are its opam packages (with version constraints). Not bad!</p>
<h2><a href="https://anil.recoil.org/news.xml#driving-scrutineer-with-a-local-model" class="anchor" aria-hidden="true"></a>Driving Scrutineer with a local model</h2>
<p>I bootstrapped the instance with the default Claude Code backend just to get going. Its initial triage (of cohttp) took Claude Opus about 13 minutes/18 agent turns, with the lighter skills completing on Sonnet in seconds.</p>
<p><img src="https://anil.recoil.org/images/scrutineer-ss-2.webp" alt="%c" title="The initial triage scan under the Claude backend."></p>
<p>I then switched the instance to an OpenCode backend, pointed at a GLM 5.3 Flash (Q4) model served from my Mac Studio by my <a href="https://tangled.org/anil.recoil.org/ocaml-deepseek">ocaml-deepseek</a> inference engine (the <code>glm-5.3</code> branch), which I <a href="https://anil.recoil.org/notes/language-integrated-llms">previously described</a>. This exposes an OpenAI-compatible endpoint, and Scrutineer's per-scan proxy routes each container's traffic to it. I was a little sad that I couldn't keep both Claude and OpenCode simultaneously active, though.</p>
<p>Using the local model is <em>much</em> slower than Claude as I've done absolutely no performance tuning yet (and for some reason, Spotlight is chewing up 100% CPU on my Mac Studio in the Golden Gate beta). I got decode speeds of around ten tokens per second, so I raised the scan timeout to eight hours to let the security deep-dives complete. While this seems slow, it's totally fine for security scans as I just left them running overnight and there's no marginal cost per scan with local models given cheap nighttime renewable electricity. <a href="https://toao.com">Sadiq Jaffer</a> is going to install GLM 5.3 on our beefy 4-GPU machine in a few days to give us a speedup, but this is fine for now.</p>
<h2><a href="https://anil.recoil.org/news.xml#my-first-findings" class="anchor" aria-hidden="true"></a>My first findings</h2>
<p>The first repo was cohttp as that was the last one I issued an <a href="https://osv.dev/vulnerability/OSEC-2026-16">advisory</a> for. The generated scan configuration first uses an agent to map its attack surface file by file, and so in the case of an HTTP parser it figured out that it needed to cover the request-line parser, the chunked transfer decoder, cookie and authorisation header parsing, and the lex/menhir grammar behind content negotiation. This is actually quite a good summary that would double as an onboarding doc for a new contributor!</p>
<p><img src="https://anil.recoil.org/images/scrutineer-ss-4.webp" alt="%c" title="The generated scan configuration maps cohttp's attack surface file by file."></p>
<p>I picked a real 'harmless' finding for the purposes of exposition here, since I obviously don't want to talk about potential real bugs. In this case, the agent decided that the <code>COHTTP_DEBUG</code> environment variable is tested for presence rather than its value, so setting it to <code>0</code> or the empty string still enables full wire logging. I don't really care enough to fix this; the agent got alarmed that it logs authorisation headers to stderr, but this is strictly a debugging flag (as the name implies) so my judgement is that it's fine as is. Note that this might not always be true: if an attacker could somehow inject environment variables as part of a chain attack, they might suddenly be able to use this to retrieve some valuable auth tokens.</p>
<p><img src="https://anil.recoil.org/images/scrutineer-ss-5.webp" alt="%c" title="A sample trivial finding where any value of COHTTP_DEBUG logs credentials to stderr."></p>
<p>Scrutineer then hands this over to a 'disclosure' workflow where it uses another agent to independently verify the bug and/or draft a vulnerability disclosure.</p>
<h2><a href="https://anil.recoil.org/news.xml#figuring-out-usable-workflows-here" class="anchor" aria-hidden="true"></a>Figuring out usable workflows here</h2>
<p>I'm pretty convinced I want to put more time into using Scrutineer now. Here are some notes (in no particular order) about what's needed to do a bigger deployment. As I type this, I left it running over the weekend on 10 more repositories and it found over 100 potential issues that need triaging!</p>
<h3><a href="https://anil.recoil.org/news.xml#supporting-multiple-backend-code-models" class="anchor" aria-hidden="true"></a>Supporting multiple backend code models</h3>
<p>The coding model backend is currently instance-wide as far as I can tell, so once I switched
to OpenCode I could no longer mix in Claude or Codex.</p>
<p>It would be quite nice for routine security deep-dives to run overnight on the
local model, but then to push promising fixes to a frontier model (since those fixes
usually aren't blocked by the cybersecurity guards, just the act of finding
them!).</p>
<h3><a href="https://anil.recoil.org/news.xml#quickndirty-multiuser-support-via-exedev" class="anchor" aria-hidden="true"></a>Quick'n'dirty multiuser support via exe.dev</h3>
<p>Since the Scrutineer UI doesn't have a login of its own, the exe.dev proxy is the only access control on a deployment like mine. I do this by running <code>ssh exe.dev share add scrutineer &lt;email&gt;</code> which grants that person <a href="https://exe.dev/docs/sharing">web access</a> to the VM via the private HTTPS proxy once they've logged into exe.dev.</p>
<p>It's therefore now possible to distinguish user requests via the <code>X-ExeDev-UserID</code> and <code>X-ExeDev-Email</code> headers that the proxy <a href="https://exe.dev/docs/login-with-exe">adds to authenticated requests</a>. That solves the immediate problem for a handful of co-maintainers, but until Scrutineer itself has user logins, triage decisions all look like they came from the same person.</p>
<h3><a href="https://anil.recoil.org/news.xml#a-git-notes-cli-workflow-would-be-amazing" class="anchor" aria-hidden="true"></a>A git notes CLI workflow would be amazing</h3>
<p>Scrutineer already has some <a href="https://github.com/alpha-omega-security/scrutineer/blob/main/docs/interchange.md">fledgling federation support</a>, to let a peer check if another instance holds the same finding before disclosing it. I haven't looked closely to verify this protocol, but I'm paranoid here as even the disclosure of the existence of bugs in a repo might be enough to trigger exploit generation.</p>
<p>Reading this did make me wonder if a more CLI-driven workflow would make it easier to cherry-pick patches and pull/push across maintainers, since we already have a very git-centric workflow for normal maintenance. When <a href="https://tangled.org">Tangled</a> gains support for <a href="https://atproto.com/blog/atproto-spaces-alpha">private repositories</a>, it would be very cool for Scrutineer to expose '<a href="https://stackoverflow.com/questions/72022248/git-refs-pull-vs-pull">magic refs</a>' like GitHub does to deal with triaging workflows. E.g. something like:</p>
<pre><code class="language-bash"># this is just a sketch of a possible CLI and not actually implemented yet
git remote add scrutineer https://scrutineer.example.com/git/mirage/ocaml-cohttp
git fetch scrutineer '+refs/findings/*:refs/remotes/scrutineer/findings/*'

git log --oneline main..scrutineer/findings/17
git diff main...scrutineer/findings/17
git cherry-pick scrutineer/findings/17 &amp;&amp; dune runtest

git notes --ref=triage/avsm add -m 'wontfix: debug-only flag, not a real issue' scrutineer/findings/17
git push scrutineer refs/notes/triage/avsm
</code></pre>
<p>Each maintainer's findings could then live in their own git notes, allowing maintainers to disagree. The overall decision of a finding would then be the merge of those refs. This is the sort of thing that <a href="https://github.com/mirage/irmin">Irmin</a> was <a href="https://anil.recoil.org/papers/2014-oud-irminsule">built for</a>! It provides Git-compatible storage with <a href="https://anil.recoil.org/papers/2015-jfla-irmin">mergeable branches</a> and a full history of user commits, although I've never tried git notes with it.</p>
<p>The more I think about it, the accept/reject step that maintainers do seems to be a really valuable part of the process here. Keeping the full set of triage decisions maintainers are making <em>across</em> repositories would feed back to subsequent scans and perhaps make a broader organisation-wide "living" threat model. It would also remove some of the mind-numbing tedium of triage a bit. This is also a reflection of my longstanding desire to have an open-source version of <a href="https://www.youtube.com/watch?v=MUqvXHEjmus">Iron</a> coming to the fore again!</p><h1>References</h1><ul><li>Madhavapeddy (2026).
