<h2><a href="https://anil.recoil.org/news.xml#geotessera-010-and-the-embeddings-explorer" class="anchor" aria-hidden="true"></a>Geotessera 0.10 and the embeddings explorer</h2>
<p>I prepared a v0.10.0 release of <a href="https://anil.recoil.org/news.xml">geotessera</a> (<a href="https://github.com/ucam-eo/geotessera/pull/374">#374</a>) that I used to finish the Zarr conversions of the v1.0 and v2-2B-L~beta1 embeddings. The latter are interesting not only for their massive accuracy improvements (the distilled v2 embeddings lead every open and proprietary embedding product tested in <a href="https://anil.recoil.org/papers/2026-tessera-v2">the v2 paper</a>), but also because of their use of <a href="https://arxiv.org/abs/2205.13147">Matryoshka embeddings</a> in which the dimensions of each embedding are ordered by importance so that a prefix of the full vector is also a usable lower-dimensional embedding.</p>
<p><a href="https://tze.geotessera.org"> <img src="https://anil.recoil.org/images/tze-v2-ss-1.webp" alt="%c"> </a></p>
<p>I added support in the latest <a href="https://github.com/ucam-eo/tze">TZE</a> that I've pushed to <a href="https://tze.geotessera.org">https://tze.geotessera.org</a> to inspect these in detail. You can now view the separate d4, d16 and d128 slices of the embeddings just by clicking on an area there, and also see it animate through time. A lot of quick analyses can happen just using the first 16 dimensions; our <a href="https://anil.recoil.org/papers/2026-tessera-v2">v2 paper</a> finds that the d16 prefix keeps around 92% of the full 128-dimensional accuracy at just an eighth of the storage.</p>
<p>Next week, I'll get the released library out at last! I just need to refresh some of the Zarr example classifier code.</p>
<h2><a href="https://anil.recoil.org/news.xml#security-holes-and-secret-agents-everywhere" class="anchor" aria-hidden="true"></a>Security holes and secret agents everywhere</h2>
<p>The Cohttp path traversal I <a href="https://anil.recoil.org/notes/2026w33">wrote about last week</a> is now fixed and released in <a href="https://discuss.ocaml.org/t/cohttp-6-3-0-released-osec-2026-16/18467">cohttp 6.3.0</a>, with the advisory published as <a href="https://osv.dev/vulnerability/OSEC-2026-16">OSEC-2026-16</a>. This, and a few other bugs that came in this week, prompted me to write <a href="https://anil.recoil.org/notes/rumour-is-the-exploit">a longer note</a> about where this is all going.</p>
<p>It weirded me out to see probes matching the exact bug pattern hit this website within minutes of my opening the public PR, and also to realise that my own agents could generate a working exploit from just a rough description of the issue class. Security embargoes no longer buy us the time they were designed to, and so we need to do either private patch development, or continuous public shipping with better release automation, and/or virtual patching/redeployments at the protocol layer to protect endpoints while the real fix winds its way through human review and packaging.</p>
<p>Some interesting responses to my post:</p>
<ul>
<li><a href="https://hachyderm.io/@Di4na/117144922813089155">Thomas Depierre argued</a> that nothing has structurally changed, as the ecosystem was already so target-rich that embargoes weren't buying much anyway, though I do think that chaining an exploit within seconds of a disclosure is a genuinely new capability.</li>
<li><a href="https://discuss.systems/@edwintorok/117145538898509590">Török Edwin suggested</a> that once a package name and vulnerability class are public, we should assume the bug is rediscoverable and publish the advisory immediately, referencing the fix commit even before a release exists.</li>
<li><a href="https://nesbitt.io">Andrew Nesbitt</a> wasted no time and has <a href="https://github.com/alpha-omega-security/scrutineer/pull/901">started on an OCaml runner profile</a> for the Scrutineer scanning I mentioned in the post.</li>
<li><a href="https://github.com/justincormack">Justin Cormack</a> <a href="https://bsky.app/profile/justincormack.bsky.social/post/3mtqsvmt7sc2t">pointed me at</a> OpenAI's <a href="https://openai.com/index/trusted-access-for-cyber/">Trusted Access for Cyber</a> programme, which he's found lightweight to use. I duly tried it but the individual verification flow rejects my cam.ac.uk account on the grounds that it "isn't available when you use a company, government, or education email address". Argh!</li>
</ul>

<h3><a href="https://anil.recoil.org/news.xml#we-need-humans-behind-opam-packages" class="anchor" aria-hidden="true"></a>We need humans behind opam packages</h3>
<p>I reviewed and merged <a href="https://github.com/dinosaure">Romain Calascibetta</a>'s <a href="https://github.com/ocaml/opam-repository/pull/30367">opam-repository#30367</a> which added a new <a href="https://github.com/ocaml/opam-repository/tree/master/governance/policies#14-package-contributors-accounts-should-have-a-human-behind-them">governance policy</a> to opam-repository that "<em>package contributor accounts should have a human behind them</em>". The <a href="https://discuss.ocaml.org/t/opam-repository-package-contributors-should-have-a-human-behind-them/18466">guidelines are</a>:</p>
<ul>
<li>A new package proposal may be submitted from a bot account, but the PR must be tagged with a human contact so maintainers know who to talk to.</li>
<li>Subsequent discussion should avoid excessive noise such as large LLM-generated responses or automated triage logs.</li>
<li>Any machine-generated comment on a package publication PR must be explicitly identified as such.</li>
<li>When human reviewers ask questions or give guidance, they must be met with human replies.</li>
</ul>
<p>The opam repository is somewhat distinct in the world of package management in that we have a team of humans who review and merge new package submissions. A small but growing number of these submissions come from projects with bot-based release procedures, and in several cases I've had to dig out who the responsible person actually is as they don't see our reviews.</p>
<p>I think this sort of guidance supersedes my <a href="https://anil.recoil.org/notes/opam-ai-disclosure">AI disclosure policy</a> proposal from earlier in the year, which was a technical solution to a governance problem.</p>

<h3><a href="https://anil.recoil.org/news.xml#eio-15-also-released-with-better-windows-support" class="anchor" aria-hidden="true"></a>Eio 1.5 also released with better Windows support</h3>
<p><a href="https://roscidus.com">Thomas Leonard</a> also released <a href="https://github.com/ocaml-multicore/eio/releases/tag/v1.5">Eio 1.5</a>. The <a href="https://notes.roscidus.com/2026/08/21/">headline features</a> are the support for Windows paths that I contributed, and the ability to set socket options before connecting (<a href="https://github.com/ocaml-multicore/eio/pull/875">eio#875</a>).
After that, I also reviewed <a href="https://patrick.sirref.org">Patrick Ferris</a>'s <a href="https://github.com/ocaml-multicore/eio/pull/923">eio#923</a> which adds environment variable support to Eio.</p>
<p>I'm still chewing on <a href="https://github.com/ocaml-multicore/ocaml-uring/pull/153">ocaml-uring#153</a> that switches the buffer type to <code>bytes</code> instead of bigarray/cstruct. I have a <a href="https://github.com/ocaml-multicore/ocaml-uring/commit/4116ced2ef40a686b0db319595561a3d53ea95ab">glorious hack</a> to keep compatibility with existing bigarray users via a fake "managed" bigarray that aliases the underlying <code>bytes</code> without copying.</p>
<p>The bigarray is allocated as a managed subarray with a hand-built proxy whose data pointer is NULL, so the runtime refcounts every derived slice but never tries to <code>free()</code> the bytes, and also a recursive finaliser closure that captures the bytes and re-registers itself until that refcount drains. This ties the bigarray proxy to the bytes as long as any bigarray view (such as a subslice) exists. This only works because the backing <code>bytes</code> is kept large enough that the OCaml 5 runtime will never move it, and there's not much performance impact if we never touch the bigarray view.  Let's see how this holds up in the next few months...</p>
