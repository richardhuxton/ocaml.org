<ul class="at-tags"><li class="published"><span class="at-tag">published</span> <p>2026-05-11</p></li></ul>
<ul class="at-tags"><li class="page-tags"><span class="at-tag">page-tags</span> <p><a href="https://jon.recoil.org/tags/odoc.html" title="odoc">odoc</a> <a href="https://jon.recoil.org/tags/day11.html" title="day11">day11</a></p></li></ul>
<p>Over the past two weeks I've been mainly wrestling with odoc.</p>
<p>I made a release of odoc - <a href="https://github.com/ocaml/odoc/releases/3.2.0/">3.2.0</a> - and a <a href="https://github.com/ocaml/opam-repository/pull/29834">PR to opam-repository</a>. In parallel, I also just managed to make an ocaml-docs-ci job that tracked the master branch of odoc. I was pretty horrified therefore to see a glaring error in the docs build of <code>base</code>.</p>
<p>It turned out that one of the patches we made for OCaml 5.5.0, to support modular explicits, had an issue. It caught me by surprise because I didn't think that anything already existed that uses this, but in fact the new constructors in the AST are being used by pre-existing language constructs, so even without source changes we were exercising the new logic. This turned out to be quite useful as it showed that there was some missing transformations in the code causing a hard failure. Fortunately the fix was ocaml/odoc#1427 "fairly straightforward".</p>
<p>With this success of the new docs ci, I thought we could do some more serious runs, so I set a job going building docs for the latest version of everything in opam using the master branch of odoc. After getting this running the following few days was spent sorting out the issues that came up - ocaml/odoc#1429 and ocaml/odoc#1431.</p>
<p>The second here showed up a problem in the fix for ocaml/odoc#930. In that, as I <a href="https://jon.recoil.org/2025/09/odoc-bugs.html" title="odoc-bugs">wrote about previously</a>, the fix was to rewrite module types being included without inline module substitutions. The code that did that effectively rewrote the following:</p>
<div><pre class="language-ocaml"><code>sig
  ...
  module Foo := Bar
  ...
end</code></pre></div>
<p>as</p>
<div><pre class="language-ocaml"><code>sig
  module Foo = Bar
end with module Foo := Bar</code></pre></div>
<p>The problem that the docs ci found was an instance that looked more like this:</p>
<div><pre class="language-ocaml"><code>sig
  module A
  ...
  module Foo := A
  ...
end</code></pre></div>
<p>and of course, in this, we can't simply do the above transformation as module <code>A</code> is only defined within the scope of the signature, so we can't reference it from outside.</p>
<p>A few months back I had rewritten this code so that rather than going through the <a href="https://jon.recoil.org/reference/odoc/odoc.xref2/Odoc_xref2/Tools/index.html#fragmap-functions" title="fragmap-functions">Fragmap functions</a> it directly used a <a href="https://jon.recoil.org/reference/odoc/odoc.xref2/Odoc_xref2/Subst/index.html" title="Odoc_xref2.Subst">substitution</a>, but I hadn't quite completed this. It seemed a good opportunity to dig it out and give it a whirl, resulting in a <a href="https://github.com/jonludlam/odoc/commit/b9791be89ffac8f947eac880766e8d88147cb74e">nice patch</a>. With the power of the new docs CI I set this going, and while it fixed <em>that</em> issue, it exposed another. At this point I felt that it was getting a bit hairy for a last-minute fix, as we needed to release odoc rather quickly for OCaml 5.5 support. So I shelved that plan, and instead went for the rather less dangerous fallback of doing nothing when we hit that pattern. The thought was that issue ocaml/odoc#930 is relatively rare, but the fragmap fix is applied to <em>all</em> includes. The 'local substitution' pattern is <em>also</em> rare, as it was only a few packages that showed the error when I did the full docs run. So the chances of hitting <em>both</em> we can expect to be even rarer! We went with ocaml/odoc#1433 "this solution" in the end.</p>
<p>The other small defect I found was an interesting one. There is an ocaml/odoc#960 "open issue" with odoc related to building docs for <a href="https://colibri.frama-c.com/">colibri2</a>. What I happened to notice with the docs ci build was that the docs build was <em>succeeding</em>. After a bit of debugging I finally figured out that this was due to missing dependency libraries during the build. Without these, it failed to do some expansions, which meant that it didn't hit the problematic case. This led to ocaml/odoc#1434 "a PR", and colibri2 is back to failing.</p>
<p>Thanks to <a href="https://github.com/panglesd">panglesd</a>'s quick review, these were merged, and we were finally able to release <a href="https://github.com/ocaml/odoc/releases/3.2.1">3.2.1</a> and put it ocaml/opam-repository#29891 "into opam".</p>
<h3><a href="https://jon.recoil.org/atom.xml#docs-ci-and-universes" class="anchor"></a>Docs CI and universes</h3>
<p>Docs CI has always had this concept of consistent "universes" of packages which are layered together. As a simplified example, imagine one universe for each version of the OCaml compiler. Then there are several versions of <code>findlib</code>, each of which can compile with each version of <code>ocaml</code>, so now we have <code>n*m</code> possible universes. Obviously this would lead to a combinatorial explosion if we wanted to have every possible universe, but in practise there's a huge amount of overlap, even when we're trying to build every version of every package. So we exploit this by having a triple that defines every build - the package name, the package version, and a hash representing the dependencies of the package.</p>
<p>A core principle of these universes is that the docs produced are <em>also</em> consistent. For example, if your package was built with OCaml 5.4.1, no matter where you click, you'll never end up on a package that was build with a different version of OCaml. Similarly for every other dependency of the package whose docs you are browsing. You will always stay within the dependency universe.</p>
<p>When we introduced "forward links" in odoc 3.0, we retained this. These forward links are links from a package's docs that should go to a reverse dependency of the package. For example, odoc's docs link to odoc-driver and odig, as examples of tools that use odoc. This is a straightforward extension of docs generation if all involved packages are already installed, as odoc has had split compile and link phases since very early versions. Compilation must be done in strict dependency order, as when odoc processes a <code>cmt(i)</code> files it requires the <code>odoc</code> files of dependencies. In contrast, linking only looks at <code>odoc</code> files, so once we've computed all of these we can link in any order we wish.</p>
<p>The approach taken in <code>ocaml-docs-ci</code> is different. Because we want to avoid processing packages more than once, we process each package individually. If a package has no forward links, we can do both compilation and linking for that package in one go. If package "a" has forward links to package "b" that depends upon "a", we have to:</p>
<p>1. compile the odoc files for package "a", 2. compile the odoc files for package "b", ensuring that the odoc files of package "a" are available 3. link the odoc files for package "a", ensuring that the odoc files of package "b" are available 4. link the odoc files for package "b", ensuring that the odoc files of package "a" are available.</p>
<p>This is obviously more complex than if there were no forward links, as then it would be just a two step process - compile and link "a", then compile and link "b". The only complixity is in ensuring that the odoc files for "a" are available when doing the compile and link for "b".</p>
<p>A further wrinkle is that your forward links might require packages with version constraints. For example, odoc might have links to documented features in odoc-driver that are only in recent versions. Even worse: there might be multiple versions of "b" that all use the same version of "a", and here we hit against the principle outlined above; that no matter where you click you never leave your universe. If there are multiple versions of "b" that link to the same version of "a", then when you click the reverse links, you must end up back on the same "b" you started with. That means there must be multiple different versions of the docs for "a", even if they're all built with the same set of build dependencies!</p>
<p>So if we're being as efficient as possible, we need to divorce the build universe from the docs universe. That way we only need to build the package "a" once, even if we build docs for it multiple times. Currently day11 <em>doesn't</em> do this, and is inefficiently doing multiple redundant builds for some packages. This doens't affect the <em>output</em> as it's the docs universes that are important there, but it does mean it's wasting resources.</p>
<h3><a href="https://jon.recoil.org/atom.xml#oi-docs" class="anchor"></a>oi docs</h3>
<p>All of which brings me on to <code>oi</code>. I had a very useful discussion with Anil on whether we need to bring all of this complexity into <code>oi</code> to build docs there. When you're working on a package in <code>oi</code>, whilst it manages many different universes, it will only instantiate one for your package. Therefore we don't need to worry so much about staying in the same universe - there can be only one.</p>
<p>So he suggested doing <em>late binding</em> of the forward links somehow, to enable building docs alongside the standard package build. The forward links would be unresolved, but we could arrange for the link to be resolved once you installed the package to be linked to. This could be done in a variety of ways. One thought I had was that I could use a branch I'd been working on a while ago which simply enumerates the possible link targets in an odocl file. The thing that makes this achievable is that we're only talking about <em>cross-package</em> references, so a lot of machinery that exists within odoc is unnecessary. We'll only allow canonical reference, and scoping isn't a problem as they will all be fully qualified references.</p>
<p>I'll be working on making this work for the rest of this week.</p>

<h4><a href="https://jon.recoil.org/atom.xml#package-api-diff" class="anchor"></a>Package API diff</h4>
<p>It's always been a nice idea to use the data we generate in docs CI in more creative ways than just producing the docs. A fairly obvious idea is to generate diffs to show what's changed in between versions of the packages. However, this was always a bit problematic because your own package doesn't necessarily uniquely define your API signatures. This is, of course, the whole reason we produce multiple universes of docs. However, in odoc 3.1 we added a neat feature that was intended to help you by only showing errors when they exist in your own packages, which worked by keeping track on a signature level of the package from which the signature came. What I realised is that we can use this info to discard diffs between package version builds so that they only show what's changed in the package being queried, rather than differences due to your dependencies.</p>
<p>A quick example. Odoc has several maps such as <a href="https://jon.recoil.org/reference/odoc/odoc.xref2/Odoc_xref2/Component/ModuleMap/index.html" title="Odoc_xref2.Component.ModuleMap">Component.ModuleMap</a> that are constructed from the standard library functor, and therefore the elements in them you can see at that link have various 'since' markers - but those all refer to the OCaml version, not the odoc version, even though these are odoc's docs. If we're trying to find the difference between two versions of odoc, we might observe differences in these just because we happened to compile the two odoc's with different compilers. Using the info put in for the warnings would eliminate this.</p>
<h4><a href="https://jon.recoil.org/atom.xml#fuzzing-odoc-parser" class="anchor"></a>Fuzzing odoc-parser</h4>
<p>We ought to fuzz odoc-parser. There are some nice tests in there - mostly expect tests - but a proper comprehensive fuzz will definitely show up some issues, as it's a hand-rolled parser. We spent some time a while back building a menhir parser, but the error paths were very hard to get working as well as the current implementation handles them. Fuzzing could help strengthen the case for using the menhir parser.</p>
<p><a href="https://gazagnaire.org">Thomas</a> has a neat <a href="https://tangled.org/gazagnaire.org/monopampam/blob/main/ocaml-claude-skills/plugins/monopam/skills/fuzz/SKILL.md">fuzzing skill</a> for Claude that he's been using to great effect with his <a href="https://gazagnaire.org/blog/2026-04-15-ccsds-protocol-stack.html">protocol development</a> work, so I'd quite like to take a look into using that to give that a whirl.</p>
