<p>In this blogpost, I'm going to show you how the data-race-freedom mode system works on the experimental <a href="https://oxcaml.org/">OxCaml</a> branch of OCaml. I recently took part in a Tarides project to test out these modes to evaluate their potential in making future multi-domain OCaml tools a reality, in particular a multicore <a href="https://github.com/ocaml/merlin">Merlin</a>, OCaml's editor service (those of you on <a href="https://tarides.com/contact/">our mailing list</a> may know what I'm talking about!).</p>
<p>This post will showcase some of what we learned and should be interesting for anyone curious about programming using multiple domains, OxCaml, editors, or just OCaml in general!</p>
<h2>What are Data Races? With Examples!</h2>
<p>A data race is a specific kind of race condition. So let's first define race conditions.</p>

<p>Here are the expected results: <code>0, 1</code> (d1 runs first); <code>1, 0</code> (d2 runs first); and <code>1, 1</code> (any other interleaving). They are predictable because each one matches a possible interleaving of the operations performed by the two domains.</p>
<p>However, another output is also possible: <code>0, 0</code>. It cannot be explained by any interleaving of the program as written, only by a reordering of instructions (due to a compiler or hardware optimisation). This can happen here because this program contains a data race.</p>
<p>By definition, data races occur in OCaml when:</p>
<ol>
<li>Two or more domains run in parallel,</li>
<li>at least two access the same mutable value,</li>
<li>and at least one of them writes to it</li>
<li>without a synchronisation mechanism (like locks or atomic operations).</li>
</ol>
<p>Non-atomic mutable values in OCaml (so values where data races can occur) include references, mutable fields of records, and arrays.</p>
<h2>How Do We Avoid Data Races in OCaml?</h2>
<p>Specific tools exist to detect data races. <a href="https://tarides.com/blog/2024-08-21-how-tsan-makes-ocaml-better-data-races-caught-and-fixed/"><code>ThreadSanitizer</code></a>, for example, detects data races at runtime. In OCaml, there are also libraries like <a href="https://ocaml.org/p/qcheck-lin/latest/doc/index.html"><code>qcheck-lin</code></a> and <a href="https://ocaml.org/p/qcheck-stm/latest/doc/index.html"><code>qcheck-stm</code></a> that help by randomly generating tests and checking for linearisability. These types of libraries are very useful when combined with TSan, which requires a lot of tests to be effective.</p>
<p>Yet, none of these solutions is static; they catch data races at runtime, and as data races are non-deterministic, they can still be missed. Other ways of preventing data races are, well, simply by not sharing mutable states between domains. However, this would imply we strongly restrict how we use multicore programming in OCaml, which would not be ideal.</p>

<h3>Preventing Data Races With Modes</h3>
<p>OxCaml adds <em>mode axes</em> to OCaml. Each axis is an independent dimension that tracks one specific property of a value, orthogonally to the others. Not every axis carries useful information for every value: the <code>contention</code> axis, for instance, controls whether a value's mutable state may be read or written from a parallel context, which only matters for mutable values (actually non-atomic ones, but we will see that later!).</p>
<p>Each axis has a small set of possible <em>modes</em> and a default one. You can pin a value's mode with an annotation, but you rarely need to: OxCaml infers modes from how values are used, as the examples throughout this post will show.</p>
<p>Of all these axes, two are what we need to guarantee data race freedom: <code>portability</code> and <code>contention</code>.</p>
<h4>Portability</h4>
<p>Portability describes whether a function can be used in a parallel context. For example, <code>Multicore.spawn</code> (which replaces <code>Domain.spawn</code>) requires as its first argument a portable function, as this function could run in a parallel context. The portability axis has 3 modes: <code>portable</code>, <code>shareable</code>, and <code>nonportable</code>. Here is what the two main modes mean (we will talk about <code>shareable</code> later):</p>
<ul>
<li><code>portable</code>: can be used in a parallel context.</li>
<li><code>nonportable</code>: can't be used in a parallel context.</li>
</ul>
<p>By default, values are nonportable: a <code>portable</code> annotation is needed to make them portable.</p>

<h4>Contention</h4>
<p>The contention axis has 3 modes: <code>contended</code>, <code>shared</code>, and <code>uncontended</code>. It only matters for non-atomic mutable values (references, arrays, or records with a mutable field): the ones that can cause a data race. Each mode controls what you may do with a value's mutable parts:</p>
<ul>
<li><code>contended</code>: neither reads nor writes are allowed.</li>
<li><code>shared</code>: reads are allowed, but not writes.</li>
<li><code>uncontended</code>: both reads and writes are allowed.</li>
</ul>
<p>So for example, with a <code>contended</code> value of type <code>{ mutable x : int; y : int }</code>, you could neither read nor write <code>x</code>, but you could still read <code>y</code>, since it is immutable.</p>
<p>The default value is <code>uncontended</code>: a value becomes <code>contended</code> when it is captured by a <code>portable</code> function. The idea is simple: if a function is <code>portable</code>, it can be used in parallel. If it captures a mutable value, to prevent data races, that value should not be accessed: it becomes <code>contended</code>. We will talk about <code>shared</code> (and <code>shareable</code> for the portability axis) later.</p>
<p>Let's see how this works in the following example:</p>

<h4>Bonus: What About <code>shareable</code> and <code>shared</code>?</h4>
<p>Note 1: As explained above, <code>portable</code>/<code>nonportable</code> and <code>contended</code>/<code>uncontended</code> are already sufficient to statically prevent data races. The <code>shareable</code> and <code>shared</code> modes are more fine-grained annotations that allow you to perform concurrent read operations on shared mutable values.</p>
<p>Note 2: The current published version of OxCaml does not completely support <code>shareable</code> and <code>shared</code> annotations. <ol>
<li>Two or more domains run in parallel,</li>
<li>at least two access the same mutable value,</li>
<li>and at least one of them writes to it</li>
<li>without a synchronisation mechanism (like locks or atomic operations).</li>
</ol>

<p>What about locks? In OxCaml, locks are provided through the <code>Capsule</code> API. Explaining it fully is beyond the scope of this article, but the general idea is this: to operate on a mutable value, you enclose it in a capsule. A capsule can be shared between domains without becoming <code>contended</code>, so every domain can still reach it. That might look like it invites data races, since it does share mutable values across domains, but accessing a capsule's contents requires exclusive access to the capsule, which a domain can only obtain through a synchronisation mechanism.</p>
<p>For the operations we are trying to do, we need the most restrictive capsule opener: a mutex. The API for mutex is not that different from the <a href="https://ocaml.org/manual/5.4/api/Mutex.html">one in mainline OCaml</a>. There is one big difference however: the mutable value lives entirely inside the capsule. The only way to reach it is by opening the capsule, which here means going through the mutex (via <code>with_lock</code>).</p>

<h2>Advanced: Interfacing OCaml Code in OxCaml</h2>
<p>When we started experimenting with making Merlin run across multiple domains, one of the main blockers we hit was code we could or would not modify, such as the OCaml typechecker that Merlin vendors. A mature codebase depends on plenty of it: external libraries, vendored modules, and legacy code written long before OxCaml. When that code holds mutable state, we face the data race problem again, but with a twist: since the code is not ours to change, we cannot add the mode annotations OxCaml relies on.</p>
<p>Let's go back to our running example, but this time assume that the <code>read</code> and <code>write</code> operations come from a vendored module we do not want to modify:</p>

<p>Replacing <code>ref</code> with <code>Atomic</code> (as we did earlier) is not an option here, since we are not allowed to touch the vendored code.</p>
<p>From the OxCaml side, all the functions exported by <code>Vendored</code> are <code>nonportable</code> (the default value) and cannot be called from a <code>portable</code> context (e.g. inside a <code>spawn</code> or a <code>fork_join2</code> callback). OxCaml provides an unsafe escape hatch with <code>Obj.magic_portable</code> which would make them callable, but it's <code>Obj.magic</code> and so it's ‘cheating’. Also, it gives the compiler no way to prevent two domains from calling them concurrently, so the mutable state inside <code>Vendored</code> would still be racy.</p>
<p>What we actually need is a way to leverage OxCaml's mode system to enforce mutual exclusion on vendored function calls at compile time, without modifying the vendored code.</p>

Neither property is checked by the compiler, so audit both by hand, ideally backed by a runtime tool like TSan.</p>
